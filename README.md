# Rental Assistant

MVP веб-приложения для арендодателя, который сдаёт 1–3 квартиры: учёт объектов, арендаторов,
договоров, арендных и коммунальных платежей, показаний счётчиков, документов и напоминаний.

Бэкенд — Go (REST API, PostgreSQL, JWT), фронтенд — React + TypeScript + Vite.
Архитектура — **modular monolith**: каждый бизнес-модуль в `internal/<module>` со своими
`handler.go`, `service.go`, `repository.go`, `model.go`.

---

## 1. Что уже работает

| Блок | Возможности |
|------|-------------|
| Аутентификация | регистрация, вход, `GET /api/auth/me`, JWT (HS256), bcrypt-хеши паролей |
| Квартиры | CRUD, площадь, описание, карточка со связанными данными |
| Арендаторы | CRUD, контакты |
| Договоры | CRUD, статусы `draft/active/terminated/expired`, срок, аренда, депозит, «истекает скоро» |
| Арендные платежи | журнал (append-only), статусы `pending/paid/overdue/canceled`, фильтры |
| Коммунальные платежи | тот же журнал с `type=utility` |
| Фиксация оплаты | `POST /api/payments/{id}/settle` — создаёт **новую** строку, исходная остаётся в БД |
| Счётчики | история показаний (append-only), последние значения по каждому счётчику |
| Документы | загрузка файла на квартиру, скачивание по токену, удаление |
| Напоминания | генерация по ближайшим платежам (7 дней) и окончанию договоров (30 дней), без дублей |
| Отчёты | сводка для дашборда: объекты, договоры, доход/расход месяца, просрочка, последние операции, динамика по месяцам |
| Изоляция данных | каждый SQL-запрос ограничен владельцем (`properties.user_id`/`tenants.user_id`), чужие объекты отдают 404 |

Сквозная проверка API на реальном PostgreSQL (43 проверки: CRUD, права, изоляция пользователей,
append-only, идемпотентность напоминаний) — см. раздел «Проверки» ниже.

## 2. Быстрый старт

### Вариант A. Docker Compose (рекомендуется)

```bash
cp .env.example .env          # поменяйте JWT_SECRET
docker compose up --build
```

Откройте <http://localhost:8080> — API и собранный фронтенд отдаются одним контейнером.
При старте контейнер сам применяет миграции (`RUN_MIGRATIONS=true`).

### Вариант B. Локально без Docker

Нужны Go 1.22+, Node.js 20+, PostgreSQL 14+.

```bash
# 1. база
createdb rental

# 2. бэкенд
export DATABASE_URL="postgres://postgres:postgres@localhost:5432/rental?sslmode=disable"
export JWT_SECRET="dev-secret-change-me-please-32-chars"
go run ./cmd/api           # миграции применяются автоматически, API на :8080

# 3. фронтенд (в отдельном терминале)
cd frontend
npm install
npm run dev                # http://localhost:5173, /api проксируется на :8080
```

Переменные окружения (все с разумными значениями по умолчанию, кроме `DATABASE_URL` и `JWT_SECRET`):

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `APP_ENV` | `development` | `development` / `production` (в production секрет JWT ≥ 32 символов) |
| `HTTP_ADDR` | `:8080` | адрес API |
| `DATABASE_URL` | — (обязательна) | строка подключения PostgreSQL |
| `JWT_SECRET` | — (обязательна, ≥ 16 символов) | ключ подписи токенов |
| `JWT_TTL` | `168h` | время жизни токена |
| `FILES_DIR` | `./data/files` | каталог файлов документов |
| `WEB_DIR` | `./web` | каталог собранного фронтенда (если есть `index.html`, отдаётся SPA) |
| `CORS_ORIGINS` | `http://localhost:5173` | разрешённые источники для dev-фронтенда |
| `RUN_MIGRATIONS` | `true` | применять миграции при старте |

## 4. Как устроены ключевые правила

**Изоляция данных.** Идентификатор владельца берётся только из JWT, никогда из тела запроса.
Каждый запрос репозитория содержит `WHERE ... user_id = $1` либо проверяет владельца через
`JOIN properties/tenants`. Обращение к чужому объекту возвращает `404`, чтобы не раскрывать
существование записи. Дополнительно проверяются связи: нельзя привязать договор к чужой квартире
или арендатору — такой `INSERT ... SELECT` просто не находит строку.

**История не перезаписывается.** В таблицах `payments` и `meters` нет методов обновления и
удаления, а в БД висят триггеры `payments_append_only` / `meters_append_only`, которые бросают
исключение на `UPDATE`/`DELETE`. Новое показание счётчика — новая строка. Оплата планируемого
платежа создаёт дочернюю запись (`parent_id`), исходный план остаётся в журнале; частичный
`UNIQUE INDEX` не даёт зафиксировать оплату дважды.

**Просрочка** не хранится в базе: она вычисляется при чтении
(`status = 'pending' AND payment_date < CURRENT_DATE`), поэтому «просроченным» платёж становится
сам по себе, без фоновой задачи и без изменения истории.

**Пароли** хранятся только как bcrypt-хеш; в ответах API хеш не участвует. JWT подписывается
HS256, в токене `sub` (id пользователя) и `exp`.

**Валидация** выполняется в сервисах (длины, форматы, суммы > 0, даты, допустимые статусы/типы)
и дублируется ограничениями `CHECK` в PostgreSQL. Все запросы — параметризованные (`$1..$n`),
SQL-конкатенации пользовательских значений нет.

## 5. Проверки

```bash
go vet ./...            # статический анализ
go test ./...           # unit-тесты бизнес-логики (auth, contracts, payments, meters, notifications)
gofmt -l .              # форматирование
cd frontend && npm run build   # tsc --noEmit + vite build
```

Unit-тестами покрыты: валидация регистрации/входа и хеширование паролей, проверки периода и сумм
договора, правила платежей и фиксации оплаты, сравнение показаний счётчиков, тексты и дедупликация
напоминаний.

Дополнительно API проверялся «живьём» на PostgreSQL 16: регистрация/логин/неверный пароль,
CRUD квартир и арендаторов, создание договора с некорректным периодом, платежи и двойная
фиксация оплаты, история счётчиков, загрузка/скачивание документа, генерация напоминаний и её
идемпотентность, сводка отчёта, изоляция между двумя пользователями (404 на чужие объекты),
401 на отсутствующий и битый токен.

## 6. API

Краткая таблица — ниже, полное описание с примерами и кодами ошибок — в [docs/api.md](docs/api.md).

```text
POST   /api/auth/register        POST   /api/auth/login        GET /api/auth/me

GET    /api/properties           POST   /api/properties
GET    /api/properties/{id}      PUT    /api/properties/{id}   DELETE /api/properties/{id}

GET    /api/tenants              POST   /api/tenants
GET    /api/tenants/{id}         PUT    /api/tenants/{id}      DELETE /api/tenants/{id}

GET    /api/contracts            POST   /api/contracts
GET    /api/contracts/{id}       PUT    /api/contracts/{id}    DELETE /api/contracts/{id}

GET    /api/payments             POST   /api/payments
GET    /api/payments/{id}        POST   /api/payments/{id}/settle

GET    /api/meters               POST   /api/meters
GET    /api/meters/latest        GET    /api/meters/{id}

GET    /api/documents            POST   /api/documents (multipart)
GET    /api/documents/{id}/file  DELETE /api/documents/{id}

GET    /api/notifications        POST   /api/notifications/generate
POST   /api/notifications/{id}/read

GET    /api/reports/summary      GET    /api/health
```

Все маршруты, кроме `register`, `login` и `health`, требуют заголовок
`Authorization: Bearer <token>`. Ошибки приходят в едином виде: `{"error": "текст"}`.

## 7. Frontend

Страницы: **Обзор** (счётчики, доход месяца, ближайшие и просроченные платежи, последние операции,
договоры, которые скоро закончатся, напоминания), **Квартиры**, **Карточка квартиры** (договоры,
платежи, счётчики, документы), **Арендаторы**, **Договоры**, **Платежи**, **Счётчики**,
**Документы**. Интерфейс адаптивный: на широком экране — боковая навигация, на узком — нижняя панель.

Токен хранится в `localStorage`, каждый запрос идёт через один клиент (`src/api.ts`);
при `401` пользователь возвращается на экран входа.

## 8. Что дальше (вне MVP)

- **S3/MinIO**: `pkg/storage` уже за интерфейсом — достаточно добавить реализацию для S3,
  раздачу файлов перевести на presigned URL.
- **AI-помощник**: распознавание актов и переписок, черновики документов — отдельный модуль,
  который читает уже существующие сущности (`payments`, `documents`) и складывает результат
  в новые таблицы; на текущем этапе не реализован.
- **Планировщик напоминаний**: сейчас `POST /api/notifications/generate` вызывается с фронтенда
  (при открытии дашборда) и из CI/крона; отдельный воркер + e-mail/Telegram-канал — следующий шаг.
- **Refresh-токены, 2FA, аудит-лог** для полноценного продакшена.

Архитектурные риски и принятые решения описаны в [docs/architecture.md](docs/architecture.md).
